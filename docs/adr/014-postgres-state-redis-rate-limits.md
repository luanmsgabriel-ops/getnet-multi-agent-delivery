# ADR 014: App state in Postgres, rate limits in Redis; mock merchant data stays in SQLite

**Context.** The v3 evaluation listed "SQLite and in-memory rate limit" as gaps under Security, Memory and Production. A single SQLite file and in-process buckets tie the API to one replica.

**Decision.**
- **App state goes to Postgres** when `STATE_DATABASE_URL` is set, which `docker compose up` does by default:
  - conversation checkpoints (`langgraph-checkpoint-postgres`, with a connection pool);
  - the handoff queue, merchant events and tickets;
  - long-term merchant memory, the spend ledger, revoked tokens and feedback.
- **One `Database` class serves both backends.** A thin adapter translates the few dialect differences: placeholders, `INSERT OR IGNORE`, `AUTOINCREMENT` and positional row access. So the stores did not need a second implementation.
- **Rate limits go to Redis** when `REDIS_URL` is set, as atomic one-minute counters per merchant and global, shared by every replica. If Redis is unreachable, the in-process limiter takes over: limits stay enforced per replica instead of disappearing.
- **Token revocation stays in the state database** (Postgres), not in Redis as first planned. It is already shared by replicas, and it is durable, so a revoked token stays revoked after a Redis restart.
- **The mock merchant tables** (sales, receivables, terminals) stay in a local SQLite file. They stand in for Getnet's own systems; in production those would be API calls, not this database.
- **No default secret:** the compose Postgres password comes from `.env`, generated by `make setup`. Compose refuses to start without it.

**Measured** (`tests/integration/test_state_backends.py`, against real Postgres and Redis locally and as CI services):
- A handoff opened on one app instance is answered on another; the operator's reply resumes the graph, the merchant gets the event, and memory is still there.
- A token revoked in Postgres is rejected by every instance.
- Two instances share one Redis rate limit: requests 1 and 2 pass, request 3 gets 429.
- A Redis outage falls back to the local limit.
- The live test caught one real bug: memory read rows by position, which SQLite allows and Postgres does not.
- On the full `docker compose` stack, a real-model chat wrote its checkpoints, memory and ledger rows to Postgres and its rate-limit keys to Redis; after `docker compose restart api` the merchant's memory and the conversation's checkpoints were still there.

**Alternatives.**
- An ORM or a second set of SQL for Postgres: more code for the same queries.
- Postgres for the mock data too: no value, since that data is a stand-in.
- Redis for revocation: faster lookups, but not durable without persistence.

**Consequences.**
- The API can run as several replicas behind a load balancer.
- Without `STATE_DATABASE_URL` and `REDIS_URL`, everything still runs from one SQLite file: tests, the hardened single-container smoke test in CI, and a quick local run.
- Two more services in compose, each with a healthcheck and a memory limit.
